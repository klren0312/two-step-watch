## 一、逻辑与状态问题

### L01｜P1｜定位回调立即覆盖新的事件横幅

- **触发**：到达标注点、持续偏航、回轨、反向或到达终点。
- **现状**：`handleFix()` 先调用 `handleEvents()` 写入 banner，随后使用回调入口保存的旧 `current` 重建 `Active`，把旧 banner 写回。新提示通常不可见，旧提示可能继续残留；震动仍会发生。
- **影响**：用户只感到震动却看不到原因，偏航和到达反馈不可靠。
- **建议**：先生成新状态，再处理事件；或让事件处理基于最新状态更新，避免使用回调入口的旧快照。
- **证据**：`NavigationSessionManager.kt:284-295`、`NavigationSessionManager.kt:346-395`。

### L02｜P1｜偏航推算进度无法可靠地向真实位置重新同步

- **触发**：偏航后继续前进，尤其存在定位跳变、平行于路线移动或推算误差累积。
- **现状**：偏航时以移动距离推算进度，单次移动最多计入 100 m；真实最近投影只在横距不超过回轨阈值时采用。推算点与真实投影分离后，静止状态不会纠正。
- **影响**：剩余里程、偏航距离、回归点、已走/未走分色和 ETA 可同时失真。
- **建议**：偏航期间仍计算并展示真实最近投影；将“导航进度估计”和“几何回归点”拆开，并增加跳变后的重同步策略。
- **证据**：`NavigationEngine.kt:314-360`、`NavigationEngine.kt:286-300`。
- **测试缺口**：现有偏航测试只有小幅连续移动，未覆盖跳变、长距离平行移动和误差重同步。

### L03｜P1｜长时间断点后大幅折返可能永久冻结进度

- **触发**：已前进较长距离，GPS 中断期间折返超过 300 m，再恢复定位。
- **现状**：最近投影相对旧进度后退超过固定的 300 m 门限即被排除；`nearest()` 返回空后保留旧快照。持续停在真实位置也无法通过该门限。
- **影响**：进度停留在旧位置，地图、回归提示和反向检测不再反映真实状态。
- **建议**：根据定位中断时长、连续匹配置信度和连续失败次数进入全局重匹配，而不是永久使用固定后退门限。
- **证据**：`NavigationEngine.kt:121-140`、`RoutePath.kt:71-90`、`RoutePath.kt:113-117`。
- **测试缺口**：`NavigationEngineTest.kt:178-185` 只覆盖前进跳变。

### L04｜P1｜过期缓存定位被当作当前定位导航和记录

- **触发**：系统保存数小时或数天前的 GPS last-known location，随后打开准备页并开始导航。
- **现状**：缓存定位没有时效检查，直接进入准备状态、导航引擎及记录器；旧坐标可成为实走 GPX 首点。
- **影响**：可从错误位置开始匹配，产生虚假的长距离记录，并使用户误以为当前定位已成功。
- **建议**：缓存定位只用于辅助显示；按单调时钟计算定位年龄，过期定位不得用于开始、匹配或记录。
- **证据**：`LocationTracker.kt:106`、`LocationTracker.kt:139-150`、`NavigationSessionManager.kt:163-200`。

### L05｜P1｜导航中定位停止更新后仍显示旧位置与旧精度

- **触发**：GPS 提供者仍开启，但隧道、遮挡或系统限制导致不再产生定位回调。
- **现状**：界面只判断 `fix == null`、精度和 provider 开关，没有定位年龄或超时状态；计时和快照也只在有效定位到来时推进。
- **影响**：旧的“±5 m”、位置箭头和剩余里程无限期保留，用户无法区分“定位良好”和“数据已冻结”。
- **建议**：增加定位超时状态与明显的“定位已中断 xx 秒”反馈； stale 数据不得继续呈现为实时精度。
- **证据**：`NavigationScreen.kt:218-225`、`NavigationScreen.kt:264-270`、`NavigationSessionManager.kt:263-300`。

### L06｜P1｜多段路线的详情里程与导航总里程口径不一致

- **触发**：导入含多个 `<trkseg>` 或多个 `<trk>` 的 GPX，且分段间存在距离。
- **现状**：详情的 `Route.distanceMeters` 只累加各段长度；`RoutePath` 则让下一段继承上一段的累计距离，段间直线距离也被算入 `totalMeters`，但地图并不绘制段间连接线。
- **影响**：详情里程、导航剩余里程、进度百分比和爬升口径互相矛盾；远距离分段会产生不存在于地图上的“里程”。
- **建议**：明确多段产品语义。若是独立分段，不计段间距离并处理跨段切换；若是连续路线，应显式绘制和说明段间连接。
- **证据**：`Route.kt:21-23`、`Route.kt:38`、`RoutePath.kt:217-251`、`NavigationMap.kt:135-151`。

### L07｜P1｜仅授予大致定位权限时陷入重复授权且无法开始

- **触发**：系统权限弹窗中只允许大致定位，COARSE 被授予而 FINE 未授予。
- **现状**：权限回调把 COARSE 也视为成功并重试；但 `hasPermission()` 只接受 FINE，准备页仍判定无权限，继续显示授权入口。
- **影响**：界面结果和实际能力不一致，用户可能反复授权仍无法开始。
- **建议**：真实导航若必须要求精确定位，应只把 FINE 视为成功，并解释原因及设置入口；若要支持大致定位，则全链路统一支持并明确精度限制。
- **证据**：`PrepareScreen.kt:67-77`、`PrepareScreen.kt:120-143`、`LocationTracker.kt:77-84`。

### L08｜P1｜启动恢复与新导航记录存在文件竞态

- **触发**：应用启动后恢复线程仍在处理较大残留文件，用户立即开始新导航并生成新的 `.part`。
- **现状**：恢复扫描不区分孤立文件和当前活动文件，可能向正在写入的文件追加尾部、复制并删除它。
- **影响**：活动记录可能提前出现 `</gpx>`、后续点写到结束标签之后，或最终导出失败。
- **建议**：启动恢复与创建新记录互斥；恢复前排除活动会话文件，并只处理确认已关闭的残留。
- **证据**：`TrackNavApplication.kt:19-30`、`TrackRecorder.kt:144-167`、`NavigationSessionManager.kt:191-200`。

### L09｜P1｜按 Home 不会关闭网页导入服务或解除常亮

- **触发**：进入网页导入页后按 Home、切换到其他应用，或打开系统 Wi-Fi 设置。
- **现状**：停服只绑定 Compose `onDispose`；应用内返回会销毁该页面，但 Activity 进入后台不必然销毁 composition。`keepScreenOn` 也在同一 effect 中设置。
- **影响**：与“离开此页即停止服务”的文案和安全预期不一致；端口与 token 可能继续可用，常亮属性也可能残留。
- **建议**：明确“离开”的产品定义，并用 Activity/生命周期状态落实；若系统设置页需要例外，应单独设计重启服务流程，而不是依赖 composition 是否恰好销毁。
- **证据**：`WebImportScreen.kt:46-59`、`WebImportScreen.kt:135-143`、`WebImportScreen.kt:188-193`、`WebImportServer.kt:80-86`。

### L10｜P1｜半截轨迹点会被恢复成 XML 无效的 GPX

- **触发**：进程在 `<trkpt>` 的多次写入或 flush 中途死亡，例如文件末尾停在 `<trkpt lat="...">`。
- **现状**：恢复只检查整个文件是否以 `</gpx>` 结尾，然后直接追加 `</trkseg></trk></gpx>`；不会回退到最后一个完整轨迹点，复制后还删除原文件。
- **影响**：生成无法解析的“已恢复”记录，且原始残留被移除。
- **建议**：截到最后一个完整 `</trkpt>` 再封装；导出后做可解析性验证，失败时保留原文件。
- **证据**：`TrackRecorder.kt:85-90`、`TrackRecorder.kt:152-167`。
- **测试缺口**：`TrackRecorderTest.kt:81-106` 只模拟完整点之间的截断。

### L11｜P1｜终点侧方明显偏航也会判定路线完成

- **触发**：当前位置投影落在终点，但实际位于终点侧方并已超过偏航阈值。
- **现状**：完成条件只检查精度和 `remainingMeters <= 25`，没有检查实际终点距离或偏航状态。
- **影响**：用户尚未到达终点就收到到达震动和“已到达终点”，并可能提前结束导航。
- **建议**：同时要求未偏航、横距在阈值内，并优先使用到真实终点的距离与短持续判定。
- **证据**：`NavigationEngine.kt:195`、`NavigationEngine.kt:272-278`。
- **测试缺口**：`NavigationEngineTest.kt:159-168` 只覆盖线上到终点。

### L12｜P1｜前台服务启动失败被吞掉，导航仍表现为正常开始

- **触发**：系统拒绝启动 location 前台服务，例如权限/后台限制或平台状态不满足要求。
- **现状**：`NavigationForegroundService.start()` 仅记录日志，不返回结果；会话仍进入 Active、获取唤醒锁并显示导航中。
- **影响**：熄屏或退到后台后定位和记录可能停止，但界面没有任何预警。
- **建议**：让服务启动结果可观察；失败时阻止进入“可靠后台导航”状态，或明确降级并提示用户。
- **证据**：`NavigationForegroundService.kt:114-121`、`NavigationSessionManager.kt:200-218`。

### U10｜P2｜持续偏航尚未成立就进入偏航态并可提示“已回到轨迹”

- **触发**：首个准确位置偏出阈值，未满 10 秒即回轨。
- **现状**：首帧立即设置 `offRouteSinceMillis` 和 `wasOffRoute`；10 秒只约束 OFF_ROUTE 事件。回轨后仍可能发出 BACK_ON_ROUTE。
- **影响**：状态含义与“持续判定”的产品描述不一致，可能出现从未提醒偏航却提醒回轨。
- **建议**：区分“候选偏航”和“已确认偏航”，只有确认后才进入偏航 UI 和产生回轨事件。
- **证据**：`NavigationEngine.kt:162-195`。

### U11｜P2｜非递增时间戳可绕过高速度过滤并污染记录

- **触发**：后续定位时间早于或等于上一个已接受点，坐标移动超过 3 m。
- **现状**：只有 `seconds > 0` 才检查速度；非递增点被接受并累计距离，导航引擎却会拒绝同类定位。
- **影响**：GPX 时间倒序、记录里程虚增，导航进度与记录内容不一致。
- **建议**：记录器拒绝非递增时间戳，并与导航引擎共享定位时效/异常过滤规则。
- **证据**：`TrackRecorder.kt:66-90`、`NavigationEngine.kt:109-114`。
- **测试缺口**：`TrackRecorderTest.kt:34-67` 只覆盖正时间差的高速度点。

### R01｜P3｜跨 ±180° 经线的路线投影和插值错误

- **触发**：路线跨越日期变更线，例如经度从 `179.999` 到 `-179.999`。
- **现状**：经纬度直接线性投影和插值，中点会落到 0° 附近，而不是 ±180° 附近。
- **影响**：路线形状、最近点、回归点和导航位置均可能错误。
- **建议**：经度差先归一化到最短路径，再投影和插值；增加跨经线测试。
- **证据**：`RoutePath.kt:93-112`、`RoutePath.kt:155-164`、`NavigationMap.kt:115-123`。

### R02｜P3｜零定位点残留会被恢复导出，与正常结束行为不一致

- **触发**：开始导航后、接受首个定位前进程死亡，下次启动恢复。
- **现状**：正常 `finish()` 会删除空记录；恢复路径却会封装并导出只有头部的 GPX。
- **影响**：产生无有效轨迹的导出文件，且该文件不满足项目解析器“至少两个有效点”的要求。
- **建议**：恢复前识别完整轨迹点数量，空残留按正常结束规则清理。
- **证据**：`TrackRecorder.kt:112-115`、`TrackRecorder.kt:144-167`。

## 二、交互与反馈问题

### U01｜P2｜纯水平或纯垂直路线的详情预览为空白

- **触发**：路线所有点纬度相同，或所有点经度相同；短直线也可能非常接近这种情况。
- **现状**：`xRange <= 0 || yRange <= 0` 时直接退出 Canvas，连起点和终点也不绘制。
- **影响**：合法的直线路线看起来像导入失败或没有轨迹。
- **建议**：为零宽/零高边界设置最小跨度并居中绘制，始终保留起终点。
- **证据**：`RouteOverview.kt:69-85`。

### U02｜P2｜罗盘不可用时“朝向朝上”静默退回北向

- **触发**：传感器缺失、精度低或尚未取得可靠方向。
- **现状**：按钮仍显示“朝向”，但 `heading == null` 时地图旋转为 0，中心箭头也变成圆点；没有“罗盘不可用/需校准”的解释。
- **影响**：用户难以判断地图实际参考方向，可能误读路线和回归方位。
- **建议**：模式标签显示当前实际状态；不可用时明确切到“北向（罗盘不可用）”，并提供校准提示。
- **证据**：`NavigationMap.kt:104-107`、`NavigationMap.kt:220-238`、`NavigationScreen.kt:231-234`、`HeadingProvider.kt:51-54`。

### U03｜P2｜导航中修改偏航阈值不会对当前会话生效

- **触发**：导航中返回路线库，进入设置修改偏航阈值，再继续当前导航。
- **现状**：设置立即持久化，震动和常亮也会动态读取；但阈值只在 `NavigationEngine` 创建时读取一次。
- **影响**：同类设置行为不一致，用户会认为当前导航已使用新阈值。
- **建议**：当前会话动态应用阈值，或在 UI 标明“下次导航生效”并禁止产生即时生效的预期。
- **证据**：`SettingsStore.kt:21-28`、`NavigationSessionManager.kt:173-182`、`NavigationSessionManager.kt:346-348`。

### U04｜P2｜记录器创建失败时没有提示，导航仍继续

- **触发**：记录目录不可创建或文件无法打开。
- **现状**：`TrackRecorder` 创建异常被 `runCatching` 转为 null，导航照常开始；直到结束总结才表现为没有有效记录。
- **影响**：用户整段行程都以为正在记录，最后才发现数据没有保存。
- **建议**：开始导航前把记录能力作为明确状态；失败时阻止开始或显示持续、不可忽略的“未记录”状态。
- **证据**：`NavigationSessionManager.kt:191-200`、`Screens.kt:319-324`。

### U05｜P2｜核心导航控件触控区域小，关键手势缺少提示

- **触发**：户外走动中点击顶部模式/缩放胶囊、底部页点，或首次使用表圈和双击全览。
- **现状**：页点点击区域只有 22 dp，视觉点只有 4–6 dp；顶部胶囊仅有约 3 dp 垂直内边距。双击全览和表圈缩放没有首次提示或屏幕内说明。
- **影响**：运动中难以准确操作，核心能力依赖猜测；小页点同时承担页面导航入口。
- **建议**：扩大实际触控区域并保持间距，提供简短首用提示；页面增加可理解的名称或当前页标题。
- **证据**：`NavigationScreen.kt:119-127`、`NavigationScreen.kt:517-546`、`NavigationScreen.kt:617-644`、`NavigationMap.kt:83-94`。

### U06｜P2｜到达终点后的结束入口过深，二次确认又长期有效

- **触发**：到达终点后想结束记录；或曾点击一次“结束导航”，离开该页后过一段时间再回来。
- **现状**：主地图只显示“已到达终点”，结束按钮位于第三页列表底部；`endArmed` 没有超时，二次确认状态会跨页面切换保留。删除轨迹的 `deleteArmed` 也没有超时。
- **影响**：到达后容易继续记录；另一方面，早已忘记第一次点击时，再一次点击就可能直接结束或删除。
- **建议**：完成后在首页提供明确主操作；所有破坏性二次确认增加短超时、离开即取消和更明显的状态样式。
- **证据**：`NavigationScreen.kt:295-300`、`NavigationScreen.kt:388-477`、`RouteViewModel.kt:191-211`。

### U07｜P2｜无定位 30 秒后可开始，但按钮仍写“等待定位”

- **触发**：准备页等待 30 秒仍无定位。
- **现状**：`canStart` 已允许开始，说明文字也写“可以直接开始”，但 `startLabel` 对 `fix == null` 永远返回“等待定位…”。
- **影响**：按钮看似仍处于禁用等待状态，用户不知道可点击。
- **建议**：30 秒后改为“无定位仍开始”，并说明开始后地图会等待首个实时定位。
- **证据**：`PrepareScreen.kt:111-116`、`PrepareScreen.kt:128-143`。

### U08｜P2｜GPX 跳过无效点的警告被丢弃，仍只显示导入成功

- **触发**：GPX 含无效轨迹点、短分段或无效标注点，但仍有足够内容可导入。
- **现状**：解析器生成 warnings，仓库只取名称、分段和标注点，报告没有警告字段；网页和 adb 导入均只展示成功/跳过/失败。
- **影响**：用户不知道路线或标注点已被删减，可能在现场依赖不完整数据。
- **建议**：导入报告保留并展示警告及数量；路线详情可再次查看导入质量信息。
- **证据**：`GpxParser.kt:84-92`、`GpxParser.kt:109-116`、`RouteStorage.kt:84-100`。

### U09｜P2｜同名标注点的到达状态和计数互相污染

- **触发**：GPX 中多个标注点名称相同，例如多个“路口”。
- **现状**：引擎按 index 记录实际到达，但快照只暴露名称 Set；列表用名称判断所有点是否到达，统计又使用名称 Set 大小。
- **影响**：到达一个同名点会把其他同名点也打勾，总数还可能少计。
- **建议**：全链路使用稳定 waypoint ID/index，不用显示名称作为身份。
- **证据**：`NavigationEngine.kt:100-103`、`NavigationEngine.kt:197-209`、`NavigationScreen.kt:368-372`、`NavigationScreen.kt:430-448`。

### U12｜P2｜网页上传可并发重入，且结果混入整个 import 目录

- **触发**：手机端重复点击/刷新重复提交，两个客户端同时上传；或 import 目录原本就有 adb 文件。
- **现状**：上传按钮没有提交中去重，服务端对每个连接独立 launch；仓库和存储没有互斥。每次网页上传都会调用 `importInbox()` 导入整个目录，而非只处理刚上传的文件。
- **影响**：并发写同一路线临时文件可能产生失败或部分成功；结果页会把其他待导入文件也算进本次上传，反馈不准确。
- **建议**：仓库导入串行化，网页只返回本次文件的报告；前端提交期间禁用按钮只能作为辅助，不能替代服务端互斥。
- **证据**：`WebImportServer.kt:61-65`、`WebImportServer.kt:169-181`、`WebImportServer.kt:214-219`、`RouteRepository.kt:39-62`、`RouteStorage.kt:108-114`。
